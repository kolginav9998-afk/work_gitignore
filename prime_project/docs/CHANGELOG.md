## [2.1.0] — контуры остатка, lot-lineage движок, атомарные документы, новые листы

Master-fix релиз по результатам внешнего аудита 2.0.1 и `POKATAK_PRIME_FINAL_WORKING_MASTER_
INLINE_STOCK.md`. Полный разбор — `docs/REQUIREMENTS_MATRIX.md` (построчно по каждому
обязательному требованию, IMPLEMENTED_VERIFIED/BLOCKED_BY_EXTERNAL_ENVIRONMENT).

### Исправлено (данные/устойчивость — наивысший приоритет)
- **COMMITTED OP_ID cache не обновлялся сразу после проведения.** `PRIME_RegisterCommittedKey`
  добавлял SOURCE_KEY только в один из двух кэшей — только что проведённый приход мог не
  попасть в остаток/FIFO в текущем сеансе до перестроения кэша. Теперь три кэша (SOURCE_KEY,
  OP_ID, DOC_ID) обновляются синхронно одной функцией.
- **FIFO/доступность не учитывали место и контур.** Выдача с конкретного места хранения
  проверяла общий остаток товара по ВСЕМ местам/контурам сразу — можно было выдать больше, чем
  реально было на выбранном месте. `PRIME_FifoLotsForProduct`/`PRIME_LocationContourBalance`
  теперь строго фильтруют по (товар, место, контур).
- **TRANSFER не сохранял партийность.** Писал два "безлотовых" движения (LOT_ID="") — партия
  физически не создавалась в новом месте, ломая дальнейший FIFO. Теперь для каждого куска,
  списанного по FIFO с исходного места, создаётся новая партия-назначение с `PARENT_LOT_ID`
  (полная трассируемость) и унаследованным возрастом FIFO (`RECEIPT_DATE`).
- **Инвентаризация не была lot-consistent.** Разница проводилась как "безлотовое" движение —
  общий остаток по месту менялся, а сумма балансов партий — нет. Теперь недостача списывается
  со специфичных партий по FIFO, излишек создаёт новую партию (origin=ADJUSTMENT).
- **Returns/Documents/Lines не фильтровались по COMMITTED.** Добавлены `PRIME_IsDocIdCommitted`,
  колонка OP_ID на DB_PRIME_DOCUMENTS/RETURNS — неудавшаяся (FAILED) операция больше не
  засчитывается как реально существующая при последующих проверках.
- **Повторные частичные возвраты могли повторно "попасть" в уже возвращённую партию.** Новая
  таблица `DB_PRIME_RETURN_ALLOCATIONS` отслеживает возвращённое количество ПО КАЖДОЙ
  конкретной allocation исходной выдачи, а не по строке в целом — второй частичный возврат
  корректно переходит к следующей партии по очереди.
- **"Провести все"-кнопки создавали N документов вместо одного.** Orders/Issues/Workflow/
  Returns/Inventory/Transfers теперь строят ОДИН `PrimeDocPlan` на весь батч отмеченных строк и
  вызывают `PRIME_PostDocument` один раз (один DOC_ID/OP_ID/один `store()`).
- **Несколько строк одного товара в одном документе не резервировали остаток друг у друга.**
  `PRIME_ValidateIssue`/`PRIME_ValidateTransfer` теперь ведут внутриплановое резервирование
  (product|location|contour) — весь документ отклоняется, если строки в сумме превышают
  реальный остаток, а не проходят по отдельности.
- **Validation создавала товар до полной проверки плана.** `PRIME_ValidateReceipt` только
  помечает `IsNewProduct`; фактическое создание вынесено в `PRIME_CreateNewProductsIfAny`,
  вызывается в `PRIME_PostDocument` сразу после успешной валидации ВСЕГО плана.
- **Критический баг, найденный этой сессией (не связан с перечисленным выше): пустая
  `SYS_PRIME_SEQ` ломала первое же действие в свежей книге.** `PRIME_ReadTable` возвращал для
  пустой таблицы "фантомную" строку из одного элемента `Empty` вместо строки правильной
  ширины — код вида `Dim newRow(UBound(table(0)))`, используемый `PRIME_SequenceNext` (и
  потенциально другим кодом по тому же паттерну), получал массив нулевой длины и падал при
  записи первого элемента. Исправлено: `PRIME_ReadTable` теперь возвращает для пустой таблицы
  "фантомную" строку правильной ширины (по числу колонок листа).

### Добавлено
- **Контуры остатка** (`SC_GENERAL`/`SC_WORKSHOP_DETAILS`/`SC_OFFICE`) — товар учитывается
  раздельно на общем складе, в деталях цеха и в офисе; STOCK_CONTOUR — новое измерение в
  DB_PRIME_LOTS/MOVEMENTS.
- **Inline-остаток на рабочих листах**: Заказы ("В наличии сейчас"), Выдачи ("В наличии" →
  "Кол-во" → "После выдачи"), Приход/Расход-Цех ("Остаток деталей" → "Приход/Расход" → "Будет
  деталей"), Приход/Расход-Офис (аналогично, "Остаток офиса").
- **Лист "Наличие"** (переименован из "Остаток", физическое переименование существующего
  листа, не создание второго) — сводный обзор с колонкой "Контур" и быстрыми фильтрами.
- **Новые листы "Перемещения"** (`PRIME_15_Transfers.bas`, TRANSFER-документ с UI) и
  **"Журнал"** (`PRIME_16_Journal.bas`, read-only список только COMMITTED документов).
- **"Комплекты" получил свою первую кнопку** ("Добавить комплект в выдачу") — лист существовал
  с 2.0.0, но ни разу не имел ни одного привязанного элемента управления.
- **Полный immutable snapshot заказа**: `DB_PRIME_ORDER_SNAPSHOT` расширен с 6 до 29 полей
  (поставщик, счёт, цена, категория и т.д.), копируется из строки "Заказы" в момент commit.
- **"Последний приход"/"Дата последнего прихода"** на листе "Заказы".
- **0 visible stubs**: 24 кнопки, ранее показывавшие "не реализовано", теперь скрыты
  (`EnableVisible=False`) вместо видимого сообщения-заглушки.
- **Upgrade-safety для существующих 2.0.x файлов**: `PRIME_Migration_UpgradeHiddenSchemaTo210`
  дописывает новые колонки (STOCK_CONTOUR, OP_ID, PARENT_LOT_ID и т.д.) в конец заголовка уже
  существующих скрытых системных листов, не трогая старые колонки/данные.
- 8 новых регрессионных тестов в `tests/model_tests.py` (итого 28/28).
- `tools/e2e_diagnostic_module.bas`/`tools/run_e2e_diagnostic.py` — диагностика прямого вызова
  `PRIME_PostDocument` в реальном headless LibreOffice (не входит в production `.ods`).

### Инфраструктура сборки
- **Найден и исправлен ещё один класс "silent chaining" дефекта**: `PRIME_Install_EnsureSchema`,
  за которым в ТОМ ЖЕ Sub/invoke() следует `PRIME_Install_EnsureBusinessSheet` для нового листа
  (`insertNewByName`), молча не создаёт этот лист — без видимого исключения. Это объясняет,
  почему "Комплекты" фактически никогда не существовал в собранных `.ods` 2.0.0/2.0.1, несмотря
  на код, который якобы должен был его создавать. Исправлено разделением на
  `PRIME_Install_EnsureSchema` и `PRIME_Install_EnsureAllBusinessSheetsOnly`, вызываемые
  сборщиком как два отдельных top-level invoke().
- `tools/build_ods.py`: `create_new_sheet_buttons` — программное создание push-button
  контролов на листах без единого пре-существующего контрола в шаблоне 1.4.1.

### Известные ограничения (см. KNOWN_ISSUES.md)
Полная визуальная переработка панели "Инфо"/"Заказы" под точный каталог кнопок мастер-задания
не выполнена (вместо неё — точечное скрытие нереализованных кнопок, R26). Диагностика
(`PRIME_13_Diagnostics`) не расширена под новые контуры/lot lineage. Полный сквозной прогон
`PRIME_PostDocument` через внешний headless `invoke()` воспроизводимо нестабилен в этой
конкретной песочнице (не подтверждает и не опровергает работу при реальном интерактивном
использовании) — см. `docs/REQUIREMENTS_MATRIX.md` R29/R30.

## [2.0.1] — стабилизация и исправление дефектов 2.0.0

Master-fix релиз по результатам `POKATAK_PRIME_2.0.1_MASTER_TASK.md`: не новая архитектура,
исправление конкретных дефектов 2.0.0, найденных при повторном разборе кода, плюс удаление
легаси-кода из production `.ods`. Полный набор фактически проверенных/не проверенных пунктов —
`TEST_REPORT.md` этого релиза.

### Исправлено (данные/устойчивость — наивысший приоритет по мастер-заданию)
- **Операционный лок больше не декоративный.** `PRIME_TryEnter` (`PRIME_01_Runtime.bas`) раньше
  всегда возвращал `True` и только считал глубину — двойной клик/повторный вход НЕ блокировался
  вовсе. Теперь это настоящий булев мьютекс, и `PRIME_PostDocument` проверяет его результат и
  отказывает в проведении, если операция уже идёт.
- **Event guard больше не "залипает".** `PRIME_EventEnter` при вложенном (уже заблокированном)
  вызове раньше увеличивал внутренний счётчик глубины И возвращал `False` — но каждый вызывающий
  использует паттерн `If Not PRIME_EventEnter() Then Exit Sub`, то есть на `False` НИКОГДА не
  вызывает `PRIME_EventLeave()`. Счётчик, увеличенный на вложенном вызове, никогда не
  уменьшался обратно — после первого же вложенного события (например, программное автозаполнение
  поля внутри обработчика) guard оставался занятым навсегда. Теперь на блокированном пути
  состояние вообще не меняется.
- **Остаток/FIFO/доступность больше не учитывают незавершённые движения.** `PRIME_LotBalance`,
  `PRIME_StockByLocation`, лист "Остаток" суммировали ВСЕ строки `DB_PRIME_MOVEMENTS` независимо
  от состояния владеющей транзакции — движения, физически записанные до `TX_COMMITTED`
  (например, при сбое между записью движений и коммитом), ошибочно увеличивали остаток. Теперь
  все три места фильтруют по `PRIME_IsOpIdCommitted(OP_ID)` (новый кэш в `PRIME_02_Store`).
- **Откат SOURCE_KEY-кэша при неудачном `store()`.** `PRIME_PostDocument` помечал `SYS_PRIME_TX`
  как `COMMITTED` и регистрировал `SOURCE_KEY` в кэше идемпотентности ДО вызова
  `ThisComponent.store()`. Если сохранение файла проваливалось, TX корректно откатывался на
  `FAILED`, но кэш — нет: повторная попытка того же `SOURCE_KEY` получала ответ "уже проведено"
  вместо повторной попытки. Добавлена `PRIME_UnregisterCommittedKey`, вызываемая в этом сценарии.
- **Почти все бизнес-листы фактически не были мигрированы в 2.0.0 (самый серьёзный найденный
  дефект).** `PRIME_Install_EnsureBusinessSheet` создаёт целевую раскладку колонок ТОЛЬКО для
  листа, которого ещё не существует — но "Выдачи" и все 4 листа "Приход/Расход — Цех/Офис",
  "Возвраты", "Инвентаризация", "Остаток", "Остаток — Заказы", "База - Поиск" уже существовали
  в шаблоне 1.4.1 (с декоративной "шапкой" из заголовка+описания перед реальной таблицей и/или
  легаси `_WMS_*`-колонками) — поэтому оставались на исходной раскладке 1.4.1, не совпадающей
  со схемой, которую ожидает остальной PRIME-код. Единственным по-настоящему мигрированным
  листом был "Заказы". Исправлено: централизованный `PRIME_FormSchemaHeaderRow`/`FirstDataRow`
  реестр (header_schema_registry — учитывает, что реальный заголовок физически не всегда в
  строке 0) и общая функция `PRIME_Migration_MigrateBusinessSheetColumns`, применённая ко всем
  затронутым листам.

### Добавлено
- `PRIME_FORM_SCHEMA` (header_schema_registry): `PRIME_FormSchemaHeaderRow`/`FirstDataRow` в
  `PRIME_00_Config.bas`; вся `PRIME_02_Store.bas` (HeaderMap/ReadTable/AppendRowsBatch/
  UpdateRowsBatch/новая `PRIME_ClearDataRows`) стала schema-aware вместо предположения "заголовок
  всегда в строке 0".
- Удаление всех 38 легаси WMS_*-модулей из собранного `.ods` (`tools/build_ods.py`,
  `remove_legacy_modules`) — раньше они оставались встроенными как "архив", только отвязанные от
  кнопок/событий. Архивные исходники остаются в git (`legacy_reference/`), не в самом файле.
- Исправлен статический текст на листе "Инфо", унаследованный от 1.4.1 и никогда не
  обновлявшийся ни одним PRIME-модулем ("Firebird: OK — embedded Firebird", версия 2.0.0).
- Регрессионные тесты в `tests/model_tests.py` на каждый из перечисленных выше дефектов
  (`test_operation_lock_rejects_reentry`, `test_event_guard_symmetric_after_blocked_nested_call`,
  `test_committed_only_stock_excludes_prepared_and_failed`,
  `test_retry_after_failed_store_is_not_treated_as_already_posted`).
- `tests/static_checks.py`: проверка, что легаси-модули отсутствуют в production `.ods`, и что
  ключевые бизнес-листы реально несут PRIME-колонки на своей физической строке заголовка.
- **Гибкий разбор даты** (`PRIME_ParseFlexibleDate`) для "Ожидаемая дата" на листе "Заказы" -
  принимает "24.08", "24/08", "24-08", с годом или без (по умолчанию — текущий).
- **Автоматический статус заказа** (`PRIME_Orders_RecomputeStatus`): Черновик/Ожидается/
  Частично получено/Получено/Просрочено, пересчитывается при вводе количества/даты и после
  проведения прихода; "Отменено" никогда не перезаписывается автоматически.
- Дополнительные фильтры остатка по категории/подкатегории/месту хранения
  (`PRIME_Stock_ShowByCategoryButton`/`ShowBySubcategoryButton`/`ShowByLocationButton`) - пока
  без привязанной кнопки шаблона, см. `KNOWN_ISSUES.md`.
- 3 новые проверки диагностики: строки документов со ссылкой на несуществующий DOC_ID,
  документы без строк, повторные COMMITTED SOURCE_KEY.
- 5 новых тестов в `tests/model_tests.py` на дату/статус (итого 20/20).

### Инфраструктура сборки
- `tools/build_ods.py`/`tests/static_checks.py`/`tools/smoke_open_save_reopen.py`: устранена
  утечка процессов `soffice.bin` (обёртка `xvfb-run` не даёт `proc.terminate()` надёжно убить
  реальный дочерний процесс) — застрявший процесс предыдущего запуска мог держать тот же
  фиксированный каталог профиля и ломать следующую сборку с невнятной ошибкой `store()`.

### Известные ограничения (см. KNOWN_ISSUES.md)
Не переносится в этот релиз: полный редизайн интерфейса (единый стиль панелей, новые листы
"Перемещения"/"Журнал", конкретный набор кнопок по мастер-заданию 2.0.1), автоматизация
"Ожидаемая дата"/статус "Просрочено" — сознательно отложено в пользу приоритетных исправлений
целостности данных (см. `KNOWN_ISSUES.md`, раздел "Не сделано в 2.0.1").

## [2.0.0] — не выпущен (в разработке)

Первая версия PRIME — полный пересмотр архитектуры относительно 1.4.1, без обязательной
зависимости от LibreOffice Base/Firebird в рантайме.

### Добавлено
- Единый posting engine (`PRIME_04_Posting.PRIME_PostDocument`) для RECEIPT/ISSUE/RETURN/
  TRANSFER/ADJUSTMENT вместо расщеплённой логики по нескольким легаси-модулям.
- Транзакционный журнал `SYS_PRIME_TX` (PREPARED/COMMITTED/FAILED) и идемпотентность по
  `SOURCE_KEY` — повторный клик не создаёт повторных движений.
- Единый рантайм-лок (`PRIME_01_Runtime.PRIME_TryEnter`/`PRIME_Leave`) на уровне всего
  документа, независимо от листа-источника.
- Единый механизм возврата (RETURN-документ на общем posting engine) вместо двух
  несовместимых легаси-реализаций.
- Обязательное поле «Назначение / проект» в `DB_PRIME_DOC_LINES` (закрывает потерю этого поля
  в 1.4.1).
- Новые функциональности, отсутствовавшие в 1.4.1: Перемещения (TRANSFER), Комплекты (лист
  «Комплекты», выдача как набор компонентов).
- 15 модулей `PRIME_00_Config` … `PRIME_14_MigrationInstaller`, единый источник схемы всех
  листов (`PRIME_*Columns()` в `PRIME_00_Config`).
- Миграция 1.4.1 → 2.0.0 листа «Заказы» с сохранением всех бизнес-колонок и генерацией
  ЕИ-кодов (см. `MIGRATION.md`).
- Тестовый набор: `tests/static_check_source.py` (проверка исходников), `tests/static_checks.py`
  (структурная проверка собранного `.ods`), `tests/model_tests.py` (модель ключевых
  алгоритмов на чистом Python).

### Известные ограничения первого релиза
См. `KNOWN_ISSUES.md` — в частности: нет UI для алиасов товара, `DB_PRIME_KITS`/`KIT_LINES` не
являются фактическим источником данных комплектов, сборка/разборка комплектов не реализована,
crash recovery для зависшей `PREPARED`-транзакции не реализован, интерактивная рантайм-проверка
проведения документов (`tests/functional_smoke.py`) не подтверждена в этом окружении.

### Не перенесено из 1.4.1 (осознанно)
- Прямая зависимость рантайма от `WMS_DATA_PORTABLE.odb` (Firebird) — не требуется для работы.
- Дублирующие модули (второй, неиспользуемый поиск; вторая, конфликтующая реализация возврата).
- Формы ввода на архивных листах «Приход/Расход — Производство, Детали» (перенесены как
  read-only история, не как активные формы).

## [1.4.1] — предыдущая архитектура (LibreOffice Calc + Basic + Firebird/Base)

Не описывается здесь подробно — см. `legacy_reference/` (архивные исходники, только для
сверки) и `POKATAK_AUDIT_2026-09-15.md` (аудит найденных дефектов, ставших основанием для
переработки в 2.0.0).
