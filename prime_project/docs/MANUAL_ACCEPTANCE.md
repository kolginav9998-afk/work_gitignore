# MANUAL_ACCEPTANCE — интерактивная приёмка ПОКАТАК PRIME 2.1.2

Этот сценарий закрывает R30 в `docs/REQUIREMENTS_MATRIX.md`, E16 в
`docs/REQUIREMENTS_MATRIX_2.1.1.md` и H16 в `docs/REQUIREMENTS_MATRIX_2.1.2.md`
(`Manual interactive acceptance в настоящем LibreOffice`). Он написан для человека, открывающего
`dist/ПОКАТАК_PRIME_2.1.2.ods` в ОБЫЧНОМ (не headless) LibreOffice Calc на реальной машине с
дисплеем — той самой проверки, которую эта разработческая песочница не может выполнить сама
(нет интерактивного дисплея, см. `docs/KNOWN_ISSUES.md`).

**Это не заявление "готово к продакшену".** Это чек-лист: пройдите каждый шаг, отметьте
факт/результат, и только после этого решайте про merge/release. Все алгоритмы уже независимо
проверены Python-моделью (`tests/model_tests.py`, 47/47) и структурными проверками собранного
`.ods` (`tests/static_checks.py`, 93/93), а ключевые сквозные сценарии этого релиза — headless
UNO-интеграционным прогоном (`tests/functional_2_1_2.py`) на реально собранном файле — здесь
проверяется то, что все три слоя в принципе не могут проверить: реальный клик мышью, реальный
`CurrentController`, реальный экран.

## Перед началом

1. Откройте СВЕЖУЮ КОПИЮ `dist/ПОКАТАК_PRIME_2.1.2.ods` (не рабочий файл с реальными данными).
2. При открытии разрешите выполнение макросов, если LibreOffice спросит.
3. Запишите версию LibreOffice (Справка → О программе) и ОС — это часть отчёта о приёмке.
4. Держите это чек-лист открытым рядом и отмечайте ПРОЙДЕНО/НЕ ПРОЙДЕНО по каждому пункту, не
   пропуская — частичное прохождение не считается приёмкой.

## Часть A — блокирующая проверка: transaction protocol нового товара (R31)

Цель — убедиться, что создание нового товара при проведении прихода происходит корректно и без
дублирования кода, при обычном (не аварийном) использовании. Полноценная проверка аварийного
сценария (сбой ровно между PREPARED и COMMITTED) требует прерывания процесса LibreOffice в
точный момент и не выполняется вручную — она покрыта fault-injection тестами в
`tests/model_tests.py` (`test_tx_protocol_*`, см. REQUIREMENTS_MATRIX R31); здесь проверяется
поведение по счастливому пути в реальном рантайме.

1. Откройте лист "Заказы". Создайте новый заказ с двумя строками НОВЫХ товаров (оставьте поле
   "Код товара" пустым, укажите только наименование) — например, "Тестовый товар А" и
   "Тестовый товар Б".
2. Проведите приход по этому заказу (кнопка "Провести"/"Провести все готовые").
   - **Ожидается:** приход проводится успешно, обеим строкам присваиваются РАЗНЫЕ ЕИ-коды без
     пропуска и без совпадения с уже существующими кодами (посмотрите на листе "Справочники"
     или через "Поиск").
3. Откройте служебный лист товаров (через администратора файла/Сервис → Макросы, если нет
   прямого доступа) и убедитесь, что обе новые строки имеют непустой `OP_ID` и видны в обычном
   поиске по коду (лист "Поиск"/"База - Поиск").
4. Повторите проведение ТОГО ЖЕ прихода ещё раз (повторный клик).
   - **Ожидается:** система сообщает, что документ уже проведён, НЕ создаёт третий/четвёртый
     новый товар и НЕ меняет уже присвоенные коды (идемпотентность по SOURCE_KEY).
5. Отметьте: ПРОЙДЕНО / НЕ ПРОЙДЕНО, с описанием отклонения при неудаче.

## Часть B — блокирующая проверка: удаление мёртвых кнопок (R26)

**Начиная с 2.1.2 лист "Инфо" скрыт по умолчанию** (не входит в авторитетный список видимых
листов — см. Часть F) — раскройте его вручную для этой проверки: правой кнопкой на любом
ярлыке листа внизу → "Показать лист..." → "Инфо".

1. На раскрытом листе "Инфо" убедитесь, что кнопки, ранее видимые как "не реализовано" (аудит и
   архитектура/чейнджлог перечисляют их полный список — `WMSC_AUDIT`, `WMSC_ACTS`,
   `WMS_CLEAN_PRODUCT`, `WMS_CLEAN_ORDER`, `WMS_CLEAN_DOC`, `WMS_CLEAN_LOT`, `WMS_CLEAN_OPER`,
   `WMS_CLEAN_ALL`, `WMS_EXPORT_REPORT_DATA`), НЕ отображаются на листе вообще — не просто
   неактивны, а физически отсутствуют.
2. Включите режим разработки форм (Вид → Панели инструментов → Формы, затем "Режим
   разработки"/Design Mode) и через Навигатор форм (F5 → вкладка "Формы" или Формы →
   Управление элементами) проверьте, что на листах "Инфо", "Заказы", "Выдачи", "Справочники",
   "Отчет — ввод" нет ЛИШНИХ (не имеющих видимой кнопки) элементов управления сверх тех, что
   реально отображаются на листе.
3. Убедитесь, что ВСЕ оставшиеся видимые кнопки на этих листах по-прежнему работают (нажмите
   каждую хотя бы один раз) — физическое удаление контролов не должно было задеть соседние
   рабочие кнопки.
4. Отметьте: ПРОЙДЕНО / НЕ ПРОЙДЕНО, с описанием отклонения при неудаче.

## Часть C — полный рабочий сценарий (создание → приход → выдача → возврат → перемещение → инвентаризация)

1. **Заказ и приход**: создайте заказ на товар, укажите ожидаемую дату (в формате "24.08" или
   "24.08.2026"), проведите приход. Запишите присвоенный ЕИ-код этой позиции. Проверьте, что
   статус заказа стал "Получено" (или "Частично получено" при частичной поставке), и "Последний
   приход"/"Дата последнего прихода" заполнились.
2. **Выдача по ЕИ-коду**: на листе "Выдачи" введите ИМЕННО тот ЕИ-код из шага 1 и выдайте часть
   количества. Проверьте, что "В наличии" на листе "Наличие" по ЭТОМУ КОНКРЕТНОМУ коду
   уменьшилось ровно на выданное количество (см. также Часть E ниже для полной проверки модели
   уникальных ЕИ-позиций).
3. **Отсутствие FIFO между разными позициями**: сделайте ВТОРОЙ, отдельный приход того же товара
   (получит ДРУГОЙ ЕИ-код — так и должно быть, см. Часть E). Попробуйте выдать по ПЕРВОМУ
   ЕИ-коду количество, превышающее его остаток, даже если второй ЕИ-код того же товара имеет
   достаточный остаток. Проверьте, что проведение БЛОКИРУЕТСЯ с сообщением вида "доступно по
   ЕИ-.../не хватает.../добавьте другую позицию отдельной строкой" — то есть система НЕ
   переключается автоматически на второй ЕИ-код.
4. **Возврат**: оформите частичный возврат по выданному документу на листе "Возвраты". Повторите
   возврат ТОЙ ЖЕ выдачи на оставшееся количество, затем попробуйте вернуть больше, чем осталось
   — последняя попытка должна быть отклонена с понятным сообщением.
5. **Перемещение**: переместите часть остатка с одного места хранения на другое (лист
   "Перемещения"). Проверьте, что суммарный остаток товара не изменился, и что партия на новом
   месте сохранила исходную дату поступления (не "помолодела" в FIFO).
6. **Инвентаризация**: на листе "Инвентаризация" загрузите текущий остаток, введите фактическое
   количество, отличное от учётного (и в большую, и в меньшую сторону для разных товаров),
   проведите корректировку. Проверьте, что остаток после корректировки равен введённому факту.
7. **Поиск/Журнал**: найдите любой из проведённых выше документов через "Поиск" и убедитесь,
   что он отображается в "Журнал" (только COMMITTED документы).
8. **Акт**: создайте акт по одному из проведённых документов (кнопка на "Отчет — ввод"/"Инфо").
9. **Сохранение/переоткрытие**: сохраните файл (Ctrl+S), закройте LibreOffice полностью,
   откройте файл заново. Проверьте, что все данные из шагов 1–8 на месте, включая остаток,
   партии, документы и журнал.
10. Отметьте по каждому шагу: ПРОЙДЕНО / НЕ ПРОЙДЕНО, с описанием отклонения при неудаче.

## Часть D — модель уникальных EI-позиций (R32/E01-E03, 2.1.1)

Цель — воспроизвести ТОЧНЫЙ сценарий из задания 2.1.1: два прихода одного товара получают
разные коды с раздельными остатками, и выдача происходит строго по явно введённому коду, без
автоматического перехода на другую позицию.

1. Создайте приход товара "Ручка" количеством 5. Запишите присвоенный код (например,
   `ЕИ-00000101`).
2. Создайте ВТОРОЙ, отдельный приход товара "Ручка" (то же наименование) количеством 19.
   Запишите присвоенный код (например, `ЕИ-00000102`).
   - **Ожидается:** код из шага 2 ОТЛИЧАЕТСЯ от кода из шага 1.
3. Откройте лист "Наличие" (кнопка "Показать всё").
   - **Ожидается:** ДВЕ отдельные строки — одна на `ЕИ-00000101` с остатком 5, другая на
     `ЕИ-00000102` с остатком 19. Они НЕ объединены в одну строку "Ручка — 24".
4. На листе "Выдачи" введите код `ЕИ-00000102` и выдайте 19.
   - **Ожидается:** остаток `ЕИ-00000102` стал 0; остаток `ЕИ-00000101` остался равен 5
     (не затронут).
5. Второй строкой того же документа выдачи введите код `ЕИ-00000101` и выдайте 1.
   - **Ожидается:** остаток `ЕИ-00000101` стал 4. Оба действия (шаги 4-5) проведены ОДНИМ
     документом (один DOC_ID).
6. Попробуйте выдать по `ЕИ-00000101` количество 5 (больше, чем оставшиеся 4).
   - **Ожидается:** проведение БЛОКИРУЕТСЯ с сообщением вида "доступно по `ЕИ-00000101`: 4
     шт. Не хватает: 1 шт. Добавьте другую позицию (ЕИ-код) отдельной строкой." Система НЕ
     переключается автоматически на `ЕИ-00000102`, даже если бы у него был запас.
7. Оформите возврат 1 шт. по строке, выданной по `ЕИ-00000102` в шаге 4.
   - **Ожидается:** остаток вернулся ИМЕННО на `ЕИ-00000102` (не на `ЕИ-00000101` и не на
     дефолтное место/контур товара, если выдача шла с другого места/контура).
8. Если в организации используются контуры "Детали цеха"/"Офис"/"Производство" — повторите
   шаги 1-2 на соответствующих активных receipt-листах ("Приход — Детали", "Приход — Офис",
   "Приход — Производство" — см. также Часть F про сами эти три листа) и убедитесь, что модель
   уникальных EI-позиций работает там так же. Расход по этим трём контурам в 2.1.2 не имеет
   отдельной активной формы (см. `KNOWN_ISSUES.md`) — используйте лист "Выдачи" для GENERAL-
   контура или сохраняйте остаток на этих контурах без расхода в рамках этой проверки.
9. Сохраните, закройте LibreOffice полностью, откройте файл заново — убедитесь, что оба
   ЕИ-кода и их индивидуальные остатки (4 и 0) сохранились корректно.
10. Отметьте по каждому шагу: ПРОЙДЕНО / НЕ ПРОЙДЕНО, с описанием отклонения при неудаче.

## Часть E — 2.1.2: "Главная", дочерние receipt-строки, новые формы прихода, видимость листов

Цель — проверить всё, что специфично для 2.1.2 (см. `REQUIREMENTS_MATRIX_2.1.2.md` H01-H13):
живое обновление дочерних строк "Заказы", лист "Главная", новые активные формы прихода, и
итоговый список видимых листов.

1. **Список видимых листов**: посмотрите на ярлыки листов внизу книги. Должны быть видны РОВНО
   13: Главная, Заказы, Приход — Офис, Приход — Производство, Приход — Детали, Выдачи,
   Возвраты, Перемещения, Инвентаризация, Наличие, Поиск, Журнал, Комплекты. Никаких других
   (в частности, НЕ должно быть видно "Приход — Цех", "Расход — Цех", "Расход — Офис",
   "Остаток — Заказы", "Дашборд", "Отчет — ввод", "Отчет руководителю", "Инфо",
   "Диагностика PRIME") — если что-то из этого видно, значит видимость не применилась
   корректно.
2. **"Главная"**: должна открываться первым листом книги. Проверьте заголовок "ПОКАТАК PRIME",
   строку версии ("Версия: 2.1.2") и строку статуса ("Статус: PRIME OK" или "Статус: есть
   ошибка диагностики (N)" — если N > 0, откройте раскрытый вручную лист "Диагностика PRIME"
   и разберитесь, что именно не так, ПЕРЕД тем как продолжать приёмку). Нажмите кнопку
   "Обновить" — сводка (незакрытые/просроченные заказы, последние операции) должна обновиться
   без ошибок.
3. **Навигация с "Главная"**: нажмите КАЖДУЮ из 12 кнопок-переходов по очереди — каждая должна
   переключать активный лист на соответствующий (Заказы, Приход — Офис/Производство/Детали,
   Выдачи, Наличие, Возвраты, Перемещения, Инвентаризация, Поиск, Журнал, Комплекты).
4. **Живое обновление дочерней receipt-строки**: создайте заказ, проведите приход (появится
   курсивная серая дочерняя строка под заказом с ЕИ-кодом, Остатком, Выдано=0, Возвращено=0).
   Выдайте часть количества по этому ЕИ-коду на листе "Выдачи" — БЕЗ дополнительного клика
   "Обновить" на "Заказы" убедитесь, что "Остаток"/"Выдано" на дочерней строке уже изменились
   сразу после проведения выдачи. Оформите частичный возврат — аналогично убедитесь, что
   "Остаток"/"Возвращено" обновились сами.
5. **"Приход — Производство"/"Приход — Детали"**: на каждом из двух листов проведите приход
   нового товара (укажите только наименование, количество, место хранения). Проверьте, что
   каждому присвоен СВОЙ ЕИ-код, и что оба кода видны на "Наличие" отдельными строками (не
   объединены с товарами из "Приход — Офис", даже при совпадении наименования).
6. Отметьте по каждому пункту: ПРОЙДЕНО / НЕ ПРОЙДЕНО, с описанием отклонения при неудаче.
