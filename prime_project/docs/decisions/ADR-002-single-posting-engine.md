# ADR-002: Единый posting engine для всех типов документов

## Статус
Принято.

## Контекст
В 1.4.1 логика проведения была размазана по нескольким модулям с независимыми путями:
расщеплённый commit (партия отдельно от движения), два несовместимых механизма возврата
(модуль 08 `RET-` с двойным commit, модуль 23 `SOURCE_ID` с одним commit — старая кнопка
возврата оставалась активной параллельно с новой), два независимых, не пересекающихся
рантайм-лока (`gWMSORD_Busy` для Заказов, `WMSDBX_TryEnter` для Выдач/цеха) — что позволяло
одновременное проведение из двух листов без взаимного исключения.

## Решение
Единственная функция `PRIME_04_Posting.PRIME_PostDocument(plan As PrimeDocPlan) As String`
пишет во все системные листы для ВСЕХ типов документов (`RECEIPT/ISSUE/RETURN/TRANSFER/
ADJUSTMENT`). Формы (Заказы, Выдачи, цеховые/офисные листы, Возвраты, Инвентаризация) строят
`PrimeDocPlan` в памяти и вызывают эту единственную функцию — сами никогда не пишут в
`DB_PRIME_*` напрямую (`ui_forms_must_not_write_movements_directly`, см. `PRIME_04_Posting.bas`
шапка файла).

## Последствия
- Единый рантайм-лок (`PRIME_01_Runtime.PRIME_TryEnter`/`PRIME_Leave`) на уровне всего
  документа закрывает конкретно найденную дыру гонки между Заказами и цехом.
- Единая последовательность шагов (идемпотентность → валидация → PREPARED → запись → COMMITTED
  → store) для всех типов документов — не нужно поддерживать 5 разных протоколов проведения.
- Добавление нового типа документа (например, ASSEMBLY/DISASSEMBLY — см. `KNOWN_ISSUES.md`)
  требует расширения одного `Select Case` в одном модуле, а не написания параллельного пути.
- Единая точка тестирования и логирования (`DB_PRIME_AUDIT`, стадии в `PRIME_00_Config`).
