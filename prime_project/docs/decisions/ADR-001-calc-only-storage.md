# ADR-001: Хранение данных только в Calc (без LibreOffice Base/Firebird в рантайме)

## Статус
Принято.

## Контекст
1.4.1 хранил часть данных в `WMS_DATA_PORTABLE.odb` (LibreOffice Base поверх embedded
Firebird), доступ шёл через отдельный SDBC-слой (`WMSDB_*` модули). Аудит
(`POKATAK_AUDIT_2026-09-15.md`) зафиксировал конкретные дефекты, связанные именно с
пересечением двух хранилищ: `WMSDB_Close` выполнял commit → store → close → store → close,
неявно подтверждая недоопределённую операцию; расщеплённый commit между
`WMS_10_DB_Stock.bas`/`WMS_12_DB_SmartReceipt.bas` мог оставить движение без партии при сбое
между двумя отдельными commit'ами в разных слоях хранения.

## Решение
Все данные PRIME — в скрытых листах одной книги Calc (`SYS_PRIME_*`/`DB_PRIME_*`,
см. `DATA_MODEL.md`). Firebird/Base не требуется для обычной работы (`Base/Firebird is not
required for runtime` — один из golden invariants). Старый `.odb` архивируется в
`legacy_reference/` только для сверки истории, не подключается по умолчанию.

## Последствия
- Один store() на документ (`ThisComponent.store()`), без параллельного жизненного цикла
  второго хранилища — устраняет саму возможность рассинхронизации между Calc и Firebird.
- Ограничение: производительность на очень больших объёмах движений зависит от эффективности
  чтения/записи листов Calc через UNO (`PRIME_ReadTable`/batched `setDataArray`), а не от СУБД
  с индексами — приемлемо для объёмов складского учёта одного пользователя/малой команды,
  не рассчитано на многопользовательскую конкурентную нагрузку.
- История из старой Firebird-базы не переносится автоматически при миграции (см.
  `MIGRATION.md`) — опционально доступна только как одноразовый read-only архив.
