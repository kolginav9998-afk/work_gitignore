# PRIME 2.0.1 — архитектура

Описывает РЕАЛИЗОВАННУЮ архитектуру (не намерение на будущее — см. `architecture_rule`).
Источники решений: `POKATAK_PRIME_2.0.0_Master_Task.md` (ТЗ), `POKATAK_AUDIT_2026-09-15.md`
(аудит), построчная карта кода 1.4.1 (см. `legacy_reference/`, SHA256 архива
`fa3da9c9c54e84a676d4aadb4607e54942c2ee056fa4f26a2a19cff7e0a265c1`, 38 модулей / 23 571 строка
Basic, 29 листов ODS).

Подробные схемы данных и транзакционный протокол вынесены в отдельные документы, чтобы не
дублироваться при изменениях кода:
- [DATA_MODEL.md](DATA_MODEL.md) — точные схемы всех системных и бизнес-листов;
- [POSTING_PROTOCOL.md](POSTING_PROTOCOL.md) — пошаговый алгоритм `PRIME_PostDocument`,
  идемпотентность, FIFO, возвраты;
- [decisions/](decisions/) — ADR по ключевым решениям (Calc-only хранение, единый posting
  engine, COMMITTED-движения как источник истины, отсутствие зависимости от Base в рантайме).

Этот документ содержит: привязку решений к конкретным дефектам 1.4.1 (§0), обработку событий
листов (§1), перечень того, что переносится/меняется/строится заново (§2), список модулей (§3).

## 0. Что заменяем и почему (привязка к найденным дефектам)

| Дефект 1.4.1 (подтверждён построчно) | Решение в PRIME |
|---|---|
| Расщеплённый commit: `WMS_10_DB_Stock.bas:373` коммитит движение, `WMS_12_DB_SmartReceipt.bas:355` коммитит партию отдельно — сбой между ними даёт движение без партии | Один `PRIME_PostDocument`: весь план документа (шапка, строки, партии, движения) собирается в памяти и пишется **одним** пакетным проходом, COMMITTED выставляется последним логическим шагом |
| Два несовместимых механизма возврата (модуль 08 `RET-`+двойной commit vs модуль 23 `SOURCE_ID`+один commit), старая кнопка возврата ещё жива | Один `RETURN`-тип документа в едином posting engine, привязка только через `SOURCE_KEY`/ссылку на исходную строку выдачи; старый путь не переносится |
| `WMSWF_IssueRowCon` (`WMS_20:461`) читает «Назначение», но не пишет его ни в один INSERT | Поле "Назначение / проект" — обязательное поле модели документа во всех формах выдачи, часть `DB_PRIME_DOC_LINES` |
| Два лока конкурентности не пересекаются (Orders: `gWMSORD_Busy`; Issues/Workshop: `WMSDBX_TryEnter`) — Orders и цеховой пост не исключают друг друга | Единый рантайм-лок `PRIME_TryEnter/PRIME_Leave` на уровне всего документа для любого проведения, независимо от листа-источника |
| `Orders_RebuildGroupContexts` при смене "групповой" колонки перечитывает и переписывает весь диапазон A1:Z (02:1278, 1824) | `PRIME_OnContentChanged` обрабатывает только изменившуюся строку через memory-index; полный пересчёт запрещён (`events.forbidden_actions`) |
| `WMSDBST_EnsureSchema`/`WMSARCH_EnsureSchema` выполняются на каждую позицию проведения | Миграция/EnsureSchema — разовая операция при открытии/обновлении, не часть posting-пути |
| `EnsureProductCon` (факт. `WMSDBST_EnsureProductCon`) вызывается до проверки повтора движения — может переписать карточку товара даже на дубликате | Порядок обязателен: сначала проверка `SOURCE_KEY` на COMMITTED-повтор, затем (и только тогда) любые изменения справочника товаров |
| `WMSDB_Close`: commit → store → close → store → close — неявно подтверждает недоопределённую операцию | Нет отдельного «закрытия БД»: `ThisComponent.store()` вызывается один раз в конце успешного проведения, транзакционное состояние (PREPARED/COMMITTED) хранится в `SYS_PRIME_TX` и переживает store независимо |
| 3 движка UI-раскладки (модули 19/31/37) с разными списками листов | Один `PRIME_12_UI`, одна команда "Восстановить интерфейс PRIME" |
| 2 реализации поиска (09 старая неиспользуемая, 24 живая) | Один `PRIME_09_StockSearch`, поиск по индексу, без параллельных путей |
| Перемещения и комплекты в 1.4.1 отсутствуют полностью | Проектируются с нуля как новые типы документов на общем posting engine, не миграция данных |
| Никакого события Open/Save/Close на уровне документа не было (office:scripts пуст) — `WMS_Close` вызывался только руками из кода | PRIME не полагается на закрытие приложения: любое непрошедшее до конца проведение обнаруживается при следующем открытии через `SYS_PRIME_TX` (crash recovery), а не через хук закрытия |

## 1. События листов

Единственный разрешённый обработчик — `PRIME_OnContentChanged`, по одному на лист ввода
(Заказы, Выдачи, 4 актуальных цеховых/офисных листа). Логика идентична для всех — не повторяем
проблему 1.4.1, где Orders и Issues имели разные, несовместимые guard-механизмы:
- определить изменившуюся строку и колонку;
- игнорировать технические колонки;
- при вводе внутреннего кода — точечный lookup по memory-index (никогда не полный пересчёт диапазона, что было причиной зависаний в `Orders_RebuildGroupContexts`);
- если положительный остаток товара ровно в одном месте — подставить «Откуда», иначе оставить пустым.

Групповые реквизиты (аналог `Orders_GroupRelevantChange`) в PRIME не пересчитываются построчным сканированием
всего листа при каждом вводе — группировка вычисляется на чтении (при построении отчётов/остатков), а не
поддерживается императивно в фоне.

## 2. Что переносим 1:1, что меняем, что строим заново

| Лист/фича 1.4.1 | Статус в PRIME |
|---|---|
| Заказы (25 бизнес-колонок + партиальные поставки) | Переносится: те же колонки, + `Получено всего`/`Осталось получить` уже есть в ТЗ; тех-колонки заменяются на 3 скрытых helper (`_PRIME_OrderID/LineID/State`) вместо 10 `_WMS_*` |
| Выдачи (12 бизнес-колонок + возврат) | Переносится, + обязательное `Назначение / проект` |
| Приход/Расход — Цех, Офис (4 активных листа) | Переносятся как единый workflow-механизм на общем posting engine |
| Приход/Расход — Производство, Детали (4 архивных листа) | Не переносятся как формы ввода: скрываются/только чтение, данные мигрируют как история (`legacy_parallel_forms`) |
| Возврат (модуль 08, кнопка на «Выдачи») | Не переносится: заменяется единым RETURN-документом; кнопка отключается |
| Возвраты (модуль 23, лист «Возвраты») | Переносится как единственный механизм возврата |
| Инвентаризация | Переносится, добавляется проверка движений после снимка (конфликт → явная обработка) |
| Остаток / Остаток — Заказы | Переносятся как view поверх COMMITTED-движений и снимков заказа соответственно |
| База - Поиск (модуль 24, живой) | Переносится как единственная реализация поиска; модуль 09 (мёртвый код) не переносится |
| Акты (ODT) | Переносятся, строятся по DOC_ID, не по текущему выделению |
| Комплекты | Новая функциональность (в 1.4.1 отсутствует) |
| Перемещения | Новая функциональность (в 1.4.1 отсутствует) |
| Дашборд, Отчёт руководителю | Переносятся с явным снимком времени обновления |
| Диагностика WMS | Переносится как реально read-only (без скрытого commit/store через общий Close) |
| WMS_DATA_PORTABLE.odb (Firebird) | Не требуется в рантайме; опционально — одноразовый read-only импорт истории |

## 3. Модули

| Модуль | Ответственность |
|---|---|
| `PRIME_00_Config` | Константы, схема всех листов (`PRIME_*Columns()`), единственный источник истины по колонкам |
| `PRIME_01_Runtime` | Рантайм-лок (`PRIME_TryEnter/Leave`), guard для событий, блокировка контроллеров на время batch-операций |
| `PRIME_02_Store` | Единственный слой прямого доступа к системным листам: чтение/пакетная запись, кэш идемпотентности (`SOURCE_KEY -> DOC_ID`), последовательности |
| `PRIME_03_Catalog` | Товарный справочник, единицы измерения, остаток по местам хранения |
| `PRIME_04_Posting` | Единый posting engine — см. `POSTING_PROTOCOL.md` |
| `PRIME_05_Orders`, `PRIME_06_Issues`, `PRIME_07_Workflows`, `PRIME_08_ReturnsInventory` | Формы ввода конкретных листов: строят `PrimeDocPlan` и вызывают `PRIME_PostDocument`, сами не пишут в `DB_PRIME_*` |
| `PRIME_09_StockSearch` | Поиск по остаткам/партиям (единственная реализация, замена двух конфликтующих в 1.4.1) |
| `PRIME_10_ActsReports`, `PRIME_11_Kits` | Акты (по DOC_ID), комплекты |
| `PRIME_12_UI` | Раскладка интерфейса, навигация, восстановление видимости листов |
| `PRIME_13_Diagnostics` | Read-only диагностика |
| `PRIME_14_MigrationInstaller` | `EnsureSchema`, миграция 1.4.1 → 2.0.0 (см. `MIGRATION.md`), резервное копирование |
