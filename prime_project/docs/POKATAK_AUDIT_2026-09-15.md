# ПОКАТАК: аудит подхода и план исправления

Дата: 15 сентября 2026. Объект: POKATAK_PRIME_LINUX_1.4.1_CLEAN.zip.

**Заключение:** сохранить привычные листы, оформление и полезные функции; переработать общий механизм проведения, события ввода и сохранение. Текущую сборку нельзя считать проверенной для рабочего учёта. В коде есть реальные дефекты, способные нарушать остатки, независимо от причины аварийного закрытия LibreOffice.

## Что действительно проверено

Проведены четыре независимых проверки: база и транзакции; заказы и производительность; складские операции; экспорт, акты, отчёт и комплекты. Основной участник сверил итоговые выводы, целостность исходников и качество проверок.

Исследован опубликованный архив, а не только старые заметки. Все 38 встроенных модулей совпали с исходниками clean_release_project/src; всего 23 571 строка Basic. SHA256 архива: `fa3da9c9c54e84a676d4aadb4607e54942c2ee056fa4f26a2a19cff7e0a265c1`.

Повторно выполнены 28 имеющихся тестов: все прошли. Они проверяют текст исходников и модели Python/SQLite. Они не исполняют реальные операции Basic/UNO/Firebird. Прохождение этих тестов при наличии перечисленных дефектов показывает недостаточность прежнего допуска сборок.

Аварийное завершение на рабочем Linux не воспроизведено: доступная здесь среда LibreOffice не содержит необходимого полноценного Firebird-драйвера для такого испытания. Пользовательская база с последними введёнными операциями не исследована. Поэтому подтверждённые дефекты кода, гипотезы причины вылета и предлагаемые изменения разделены ниже. Полный цикл фактически выполненных операций на Linux в этом аудите не заявляется.

## Почему зависание возможно уже на одном заказе

Сильнейший кандидат при нажатии «Новый заказ» — обработка изменений листа:

1. `Orders_CreateNewEntryWithSource` в модуле 02 снимает gWMSORD_Busy до вызова Orders_ProcessRow (строка 4082).
2. Orders_ProcessRow программно меняет множество ячеек. Лист действительно связан с Orders_OnContentChanged в опубликованном ODS.
3. Обработчик не исключает изменения только технических колонок. Даже при неизменных пользовательских данных он может поячейково сканировать все SourceID, переоформлять строку и обновлять фильтр.
4. Изменение одного общего реквизита заказа вызывает Orders_RebuildGroupContexts: читает диапазоны всех заказов, пересчитывает группы и записывает весь технический диапазон. Затем выполняется ещё один проход по связанным строкам.

Это подтверждённый путь лишней работы и неполной защиты программных изменений. Бесконечная рекурсия и конкретный нативный краш не доказаны: внутри обработчика есть собственная защита.

Если вылет происходит при «Провести», главный отдельный кандидат — обслуживание базы внутри каждой строки: проверки схемы, массовое дозаполнение истории, пересоздание представлений, заполнение справочников, несколько commit и циклы сохранения/закрытия. Эти действия не должны сопровождать каждую новую позицию.

Если зависает именно «Обновить WMS», нужен отдельный след выполнения обновления. В 1.4.1 широкая перестройка убрана из обычного WMS_UPDATE, но остаётся в WMS_REPAIR. Изменение установщика не исправило обработчики заказов.

Для точной локализации требуется журнал с независимыми этапами: вход в кнопку → начало/конец обработчика → проверка строки → запрос базы → commit → сохранение ODB → обновление листа. Записывать номер операции, счётчики повторных событий, длительность и полный SQLSTATE/код ошибки, без содержимого коммерческих документов. При нативном закрытии дополнительно нужен системный журнал/дамп LibreOffice; последний этап приложения только сужает поиск, но не доказывает причину.

## Независимое предложение участника 1: база и сохранение

**Заменить несколько цепочек записи единым сервисом проведения.**

Подтверждённые проблемы:

- В `WMSDBST_PostMovementClassifiedCon` (10, строка 373) движение фиксируется COMMIT до создания и привязки партии в `WMSDBSR_PostReceiptCon` (12). Следующий commit выполняется в 12, строка 355. Сбой между ними оставляет частично оформленную операцию. Откат после первого commit уже не отменит сохранённое движение.
- На каждую строку вызывается `WMSDBST_EnsureSchema` → `WMSARCH_EnsureSchema`. Модуль 21 проверяет структуру, обновляет старые записи, пересоздаёт два VIEW, выполняет семь заполнений справочников INSERT…SELECT и commit. Нагрузка растёт с историей склада и повторяется при каждой позиции.
- `EnsureProductCon` вызывается до проверки повтора движения и может заменить карточку товара, включая базовую единицу и пустой артикул, даже когда повторное движение не добавлено.
- В некоторых путях синхронизации заказов ошибки commit подавляются; результат SaveDatabaseDocument игнорируется. Наличие записи в текущем соединении не равно подтверждению сохранённого файла.
- `WMSDB_Close` одновременно делает commit, сохраняет ODB, закрывает соединение, снова сохраняет ODB и закрывает документ. Процедура закрытия не должна неявно подтверждать неопределённую незавершённую операцию.
- Лимиты полей не согласованы: например, комментарий заказа допускает больше символов, чем комментарий движения; название места может быть длиннее REF_CODE справочника. Допустимый ввод может упасть на последующей стадии.

Новый контракт: проверить весь документ → начать транзакцию → записать заголовок, все строки, снимок заказа, партии и движения → сверить ожидаемый результат → один commit → подтвердить сохранение → очистить ввод. Вспомогательные функции не выполняют DDL, commit, rollback или store. Миграции выполняются один раз по версии, отдельно от учёта.

Для ODB нужно отдельно проверить долговременное сохранение на целевой версии LibreOffice. SQL-транзакция, упаковка ODB и сохранение Calc — разные границы отказа. Не следует обещать общую атомарность этих файлов одной командой. Устойчивый ID операции и журнал состояний позволяют после перезапуска определить, что уже сохранено, и безопасно завершить интерфейсный шаг без повторного движения.

## Независимое предложение участника 2: ввод заказов и скорость

**Оставить знакомую таблицу, сделать ввод локальным и лёгким.**

- Весь программный ввод выполнять под единым вложенным счётчиком блокировки событий с обязательным восстановлением при ошибке.
- События технических колонок сразу исключать из обработки.
- При редактировании проверять текущую строку и её заказ; не переписывать техническую часть всей истории.
- Группу заказа хранить явным ID. Номера позиций 1–5 могут повторяться в следующем заказе, но не служат его глобальным идентификатором.
- Фильтр расширять при добавлении строк, оформление применять один раз при создании/импорте. Поиск ID и групп выполнять по индексу, а не поячейковым проходом.
- Назначение и ожидаемую дату включить в единый перечень полей. Сейчас обычный fingerprint охватывает A:W, а расширенная синхронизация живёт отдельно.
- Обработчик вставки молча ограничивается 2500 строками, специальный импорт допускает 20 000. Требуется единый режим пакетной обработки с видимым результатом по всем строкам.
- Импорт сейчас может отклонить новый самостоятельный документ из-за совпадения содержимого строки. Защита от повторного файла/документа должна отличаться от допустимого повторения товаров.

Разделение действий: ввод сохраняет черновик и проверяет реквизиты; «Провести» меняет склад; обновление остатков и отчётов читает уже сохранённые данные. Автоматизация сохраняется, но тяжёлые действия перестают выполняться на каждую ячейку.

## Независимое предложение участника 3: складские операции

**Одна идентичность товара и одни правила движения для всех форм.**

Критический конфликт возвратов: новый механизм в модуле 23 создаёт движение с независимым MOV-… и связывает его через SOURCE_ID. Старый механизм 08 ищет движение только по MOVEMENT_ID='RET-'||RETURN_ID. Поэтому корректный новый возврат может быть признан незавершённым. Старая кнопка возврата присутствует в реальном ODS и вызывает автоматическое восстановление; оно способно добавить второй приход. Это достижимый конфликт кода; не утверждается, что пользователь уже получил именно такой дубль.

Назначение в расходе цеха считывается в `WMSWF_IssueRowCon`, но не записывается в таблицы документа, выдачи или движения. После очистки ввода это значение теряется. Следовательно, отчёт по назначениям нельзя надёжно построить для этих операций без исправления записи.

Возвраты и инвентаризация отличаются от ручного прихода: после закрытия базы не выполняют такое же подтверждение сохранения через повторное чтение, а защитный признак ошибки закрытия не проверяют. В нескольких запросах остались SUM без приведения типа, хотя ранее уже возникала ошибка SQLDA при чтении агрегата. Несогласованность кода подтверждена; повторение именно той ошибки в каждом запросе требует проверки драйвера.

Старые выдачи в модуле 07 также последовательно сохраняют выдачу, распределение партии и движение отдельными шагами; возврат 08 сначала фиксирует возврат/возвращённое количество, затем движение и партию. Следовательно, проблема ранних подтверждений относится не только к заказам. Новый FIFO умеет распределять расход между партиями, старый путь всё ещё требует одну выбранную партию. Разные кнопки не должны давать разные правила списания. Нужно согласовать округление Double с фиксированной точностью количества в таблицах.

Экран остатков ограничен 2000 строками с предупреждением. Этот предел не объясняет исчезновение 126 введённых позиций; нельзя списывать прежнюю проблему на ограничение экрана. Старые формы сопоставляют товар по артикулу без такого же контроля наименования/единицы, как новая форма цеха. Артикул должен иметь контекст поставщика и не заменять внутренний код.

Исправление: одна функция проведения документа с типами «Приход», «Выдача», «Возврат», «Перемещение», «Корректировка». Производство и детали — единый цеховой интерфейс с категориями, а не разные бухгалтерии. Офис может оставаться отдельным удобным представлением того же механизма.

Внутренний код — постоянная идентичность товара, артикул поставщика — необязательный дополнительный реквизит. Товар без артикула выбирается по внутреннему коду. Новый код показывается пользователю до очистки и остаётся доступным в журнале/печати наклейки. Совпадение названий не должно автоматически объединять разные товары, а повторный приход существующего товара не должен создавать новый код без явного решения.

FIFO оставляем автоматическим: одна выдача может списывать несколько партий. Длинный LOT-ID не требуется вводить вручную в обычном сценарии. При необходимости ручного выбора показываем дату, документ, место и доступное количество. Возврат связывается с исходной выдачей; возвращать сверх выданного за вычетом предыдущих возвратов нельзя.

## Независимое предложение участника 4: акты, отчёт, экспорт и комплекты

**Все представления должны опираться на один сохранённый документ.**

Экспорт:

- Старый экспорт повторяет общий остаток товара в каждой строке его заказов; новый считает остаток партии. Их нельзя показывать как один и тот же суммируемый показатель.
- `WMSX_OrderStockRefresh` очищает старый результат перед записью нового. При ошибке старая отметка «Обновлено» может сохраниться, а экспорт доверяет этой надписи. Нужен явный успешный снимок с версией/временем; при неудаче результат нельзя выдавать за актуальный.
- Новый экспорт делает отдельный запрос снимка на каждую строку и ReDim Preserve на каждую добавленную запись. Снимки нужно читать пакетно, массивы выделять блоками.
- Все исходные поля заказов сохранять неизменяемым снимком при проведении. В исторических данных, где снимка нет, явно показывать отсутствие; не восстанавливать историю выдуманными значениями из нынешней строки.

Акты:

- Сохранение ODT и предложение открыть Writer уже реализованы; это сохранить.
- Цеховой акт читает артикул C и игнорирует внутренний код L. Для товаров без артикула теряется идентификатор.
- Акт строится из текущего выделения, а после проведения ввод очищается. Нужно формировать акт по сохранённому документу и повторно открывать из журнала. До проведения допускается явно обозначенный черновик.
- Ошибки записи ячеек Writer и преобразования количества местами подавляются. Нужны строгая проверка и отказ от сообщения об успехе при неполном акте.
- Файл ODT и реестр создаются последовательно. Требуются состояния формирования и повторное завершение регистрации, чтобы сбой не оставлял «файл есть, в журнале нет» без возможности восстановления.

Отчёт руководителю:

- Автоматические факты: число документов поставки, число строк, число разных товаров; приёмка/выдачи/возвраты по единицам; получатели и назначения; ожидаемые/просроченные поставки; недостачи и излишки; незакрытые документы; выполненные сборки; проблемы, требующие решения.
- Не считать количество строк числом поставок: сейчас OPERATION_ID в ручном вводе может соответствовать одной строке.
- На листе настройки/ввода: период, автор, подразделение, короткие карточки «Погрузчик», «Помощь», «Закупки», «Бухгалтерия», «Расхождение». Из связанного документа автоматически подставляются дата, поставщик, номер и позиции; вручную отмечаются факт работы, результат и следующий шаг.
- Примеры формулировок: «Выполнена механизированная разгрузка поставки №…»; «Согласовано устранение расхождения по количеству…»; «Переданы закрывающие документы по поставке…». Формулировка создаётся из отмеченного события, а не из предположения.
- На втором листе — готовый отчёт. Его сохранённая версия фиксирует дату и данные периода; последующее изменение склада не должно переписывать уже отправленный отчёт.

Комплекты:

| Режим | Что делает пользователь | Что происходит с остатками |
|---|---|---|
| Набор для выдачи | Выбирает набор и количество, например «2 крепления + 4 болта» | Заполняется обычный расход компонентами. Отдельный остаток набора не создаётся |
| Физическая сборка | Проводит документ сборки по сохранённому составу | В одной транзакции списываются компоненты и приходуется комплект с собственным внутренним кодом |
| Разборка | Выбирает ранее собранный комплект и количество | Комплект списывается, пригодные компоненты возвращаются отдельными движениями; потери оформляются явно |

Первым целесообразен набор для выдачи: он проще и использует существующую выдачу. Для физической сборки нужны версия состава, фактически использованные партии, связь входов/выхода и единицы измерения. Вложенные комплекты сначала лучше запретить; позже разрешать только с проверкой циклов. Состав проведённой сборки неизменяем. Недостача любого компонента отменяет всю сборку. Повторное нажатие не создаёт второй комплект. При двух креплениях и четырёх болтах на комплект, запасе 10 креплений и 30 болтов доступно 5 комплектов до учёта резервов. Нельзя одновременно показывать израсходованные компоненты свободными и прибавлять готовые комплекты.

## Дополнительный вывод основного участника: диагностика не является доказательством исправности

`WMSINT_CheckText` выводит число движений без партии, но не увеличивает nProblems для этой проверки. Поэтому счётчик проблем может не отражать важный дефект партийного учёта. Сумма QTY по всем единицам не имеет смысла как складской итог: штуки, метры и килограммы необходимо проверять раздельно.

Диагностика помечена «Только чтение», но вызывает общий WMSDB_Close, содержащий commit/store. Нужно отдельное действительно читающее подключение/режим без скрытого подтверждения записи. Проверять следует не только присутствие таблиц и ID, но и равенство количеств, связи документов и партий, двойные возвраты, незавершённые операции, сохранность реквизитов и актуальность выгрузок.

## Целевой рабочий цикл и критерии приёмки

| Операция | Требуемое поведение и проверка |
|---|---|
| Новый заказ | Создать строку без записи на склад и массовой обработки истории; сохранить назначение и ожидаемую дату |
| Импорт | Предпросмотр, перенос реквизитов объединённых ячеек только внутри своего заказа, учёт всех строк, отчёт об ошибках и повторах |
| Частичная поставка | Заказ 10, пришло 6, затем 4: два документа/партии, факт 10, открыто 0, сохранена история обоих документов |
| Цеховой приход | 126 строк с разными и повторяющимися товарами: сверяются все строки и количества; агрегированный остаток может содержать меньше строк по понятной причине |
| Выдача | Автоматическое списание из нескольких партий; сохраняются получатель, назначение, место и единицы; нехватка запрещает весь документ |
| Возврат | Возврат 2 после выдачи 5 увеличивает склад ровно на 2; повтор не увеличивает снова; остаток к возврату 3 |
| Перемещение | Одинаковое количество списано с одного места и принято на другое; суммарный запас не изменился |
| Инвентаризация | Зафиксирован момент/область проверки; движение между подсчётом и проведением выявляется; записывается разница, исходная история сохраняется |
| Исправление | Сторно/корректирующий документ со ссылкой и причиной; рабочую историю не исправляют массовым удалением |
| Комплект | Компоненты списаны, комплект добавлен одним документом; нехватка/сбой не оставляет половину сборки |
| Акт | Из журнала сохранённого документа; внутренний код виден; ODT открывается по предложению, PDF только отдельной командой |
| Остатки/поиск | Один источник расчёта, одинаковые фильтры, сверка по товару/единице/месту и партиям |
| Остаток по заказам | Все сохранённые реквизиты и остаток соответствующей партии, включая нулевой; общий остаток товара не дублируется как итог каждой поставки |
| Дашборд/отчёт | Отдельное обновление, видимая дата актуальности; ошибка не публикует частичный снимок |
| Закрытие/повторный запуск | Все подтверждённые документы и реквизиты сохранены, неопределённые операции сверяются без дублей |
| Обновление сборки | Проверка версии, резервная копия пользовательских данных, однократная миграция, контроль и возможность возврата |

Эта таблица — спецификация испытаний, а не утверждение, что указанные операции уже успешно выполнены в текущей версии.

## Что менять в первую очередь

1. **Зафиксировать исходную версию и локализовать вылет.** На копии воспроизвести отдельно открытие, новый заказ, ввод ячейки, проведение и обновление. Собирать этапы/длительность. Исправить защиту событий и прекратить широкие пересчёты при вводе.
2. **Сделать единое проведение и сохранение.** Убрать внутренние commit и DDL; согласовать длины полей, единицы и идентификаторы; единый журнал документов, стабильные ID, сверка результата и восстановление после неопределённого исхода.
3. **Перевести все формы на этот механизм.** Заказы, цех, офис, выдачи, возвраты, инвентаризация. Удалить конфликтующий возвратный путь из рабочего интерфейса. Сначала обследовать существующие данные; не запускать слепое восстановление.
4. **Исправить акты и выгрузки.** Документ — источник акта; снимок заказа — источник исторических реквизитов; единая семантика остатка; пакетное чтение, явная актуальность.
5. **Затем автоматизация отчёта и комплекты.** Использовать общее проведение, не добавлять ещё одну отдельную систему записи.

Смена Firebird сама по себе не исправит ранние commit, двойные возвраты и события Calc. Первое рекомендуемое решение — сохранить интерфейс, заменить внутренние правила работы. Если после этого изолированный тест выявит воспроизводимый дефект встроенного Firebird на целевом Linux, отдельно сравнить локальную внешнюю БД или автономное приложение. Такой переход требует миграции и проверки офлайн-развёртывания; пока он не является доказанно более простым вариантом.

В рабочей папке оставить книгу, базу и необходимые ресурсы. Установочные исходники, тесты и прежние архивы не смешивать с работой. При этом убрать старые бэкапы из поставки не значит отключить резервное копирование уже введённых пользователем данных: резервные копии создаются отдельно от папки повседневной работы и управляются понятной политикой хранения.

## Когда можно называть сборку проверенной

- Реальный LibreOffice на целевом Linux, чистый запуск и повторное открытие; Windows — отдельная проверка при заявленной поддержке.
- Нагрузки 1, 126 и 1000 строк документов; ввод на фоне 0, 1000 и 10 000 исторических строк.
- Ошибка после каждой стадии проведения: до записи, после части строк, перед commit, после commit, при сохранении ODB и перед очисткой Calc. После перезапуска — полный документ либо отсутствие его движений; неопределённый исход видим и сверяем, повтор не удваивает.
- Частичная приёмка, одинаковые товары, отсутствие артикула, дробное количество, разные единицы, длинные реквизиты, запятая в числе, кириллические пути, файл только для чтения, нехватка места, повторный клик.
- Сверка каждой строки и всех итогов по единицам; совпадение в журнале, остатках, поиске, актах и выгрузках.
- Замеры на целевом компьютере с объёмом базы. Предлагаемые ориентиры, а не обещанные результаты: обычный ввод около 0,2 секунды, создание строки до 1 секунды. Для пакетных операций — измеряемая длительность, индикатор этапа и завершённости; отмена только там, где она не оставит неопределённую запись.
- Проверка обновления и возврата к предыдущей версии на копии, без подмены пользовательской базы пустой базой из архива.

Без этих испытаний новую надпись PRIME нельзя приравнивать к готовности к работе. В рамках этого аудита исходники и пользовательские данные не изменялись, новая сборка не выпускалась.

## Техническая опора для вывода о транзакциях

Документация LibreOffice XConnection определяет commit как подтверждение изменений после предыдущего commit/rollback, а rollback — отмену изменений после этой границы. Поэтому поздний rollback не отменяет ранний commit из вложенного помощника: [LibreOffice XConnection](https://api.libreoffice.org/docs/idl/ref/interfacecom_1_1sun_1_1star_1_1sdbc_1_1XConnection.html). Документация подтверждает семантику API, но не доказывает причину аварийного завершения конкретной версии LibreOffice.
