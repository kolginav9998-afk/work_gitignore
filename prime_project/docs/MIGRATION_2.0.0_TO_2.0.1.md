# Миграция 2.0.0 → 2.0.1

2.0.1 — релиз исправлений, не новая архитектура. Если у вас уже есть рабочий файл, собранный
из версии 2.0.0 (`SYS_PRIME_META.SCHEMA_VERSION = "2.0.0"`), при следующем открытии/пересборке
произойдёт следующее.

## Что произойдёт автоматически при миграции существующего файла

Нажатие кнопки "Обновить" на листе "Инфо" (`PRIME_Migration_RunButton`) на файле 2.0.0:

1. Создаётся резервная копия (как и раньше).
2. **Впервые фактически применяется целевая раскладка колонок** к листам "Выдачи",
   "Приход — Цех", "Расход — Цех", "Приход — Офис", "Расход — Офис", "Возвраты",
   "Инвентаризация", "Остаток", "Остаток — Заказы", "База - Поиск"
   (`PRIME_Migration_MigrateAllBusinessSheets`, новое в 2.0.1). Если ваш файл 2.0.0 уже
   содержал данные на этих листах, введённые ВРУЧНУЮ (не через кнопки PRIME, так как кнопки
   PRIME в 2.0.0 писали и читали по неверным колонкам из-за самого этого дефекта — см.
   `CHANGELOG.md`), эти данные будут перенесены **по имени колонки, где это возможно**; поля,
   которых нет в целевой схеме (в частности, всё ещё остававшиеся легаси `_WMS_*`-колонки),
   переноситься не будут.
3. Миграция листа "Заказы" и генерация ЕИ-кодов — без изменений от 2.0.0.

## Что НЕ требует действий пользователя

- Исправления операционного лока, event guard, фильтра "только COMMITTED влияет на остаток" и
  отката SOURCE_KEY-кэша — это исправления поведения кода, они начинают действовать сразу
  после пересборки/обновления модулей, без миграции данных.
- Удаление легаси WMS_*-модулей из файла — если вы никогда не вызывали их напрямую (кнопки уже
  были перепривязаны на PRIME_* в 2.0.0), поведение не меняется, файл просто становится легче.

## На что обратить внимание после обновления

- **Проверьте остаток на листе "Остаток" после обновления.** Поскольку в 2.0.0 остаток мог
  включать движения незавершённых операций (см. `CHANGELOG.md`, пункт про committed-only
  stock), число на листе "Остаток" после обновления до 2.0.1 может измениться (уменьшиться),
  даже если реальный физический остаток на складе не менялся — это исправление ошибочного
  завышения, а не потеря данных. Если расхождение существенное, сверьте с `DB_PRIME_AUDIT`/
  `SYS_PRIME_TX` (проведение → "Диагностика") на предмет старых `PREPARED`/`FAILED`-записей.
- **Если на листах Выдачи/workflow-листах/Возвраты/Инвентаризация/Остаток были данные,
  введённые вручную поверх декоративной "шапки" 1.4.1** (то есть до исправления в 2.0.1 эти
  листы физически ещё не имели PRIME-раскладки) — после миграции проверьте, что перенесённые
  строки совпадают по колонкам с ожидаемым (см. `DATA_MODEL.md`).

## Откат

Резервная копия, созданная перед миграцией (`Backups/POKATAK_backup_*.ods`), содержит
состояние файла ДО миграции 2.0.1 — используйте её, если после обновления обнаружены
расхождения, которые не удаётся объяснить исправлениями выше.
