# PRIME 2.0.0 — целевая архитектура

Источники: `POKATAK_PRIME_2.0.0_Master_Task.md` (ТЗ), `POKATAK_AUDIT_2026-09-15.md` (аудит),
и построчная карта кода 1.4.1 (см. `legacy_reference/`, SHA256 архива
`fa3da9c9c54e84a676d4aadb4607e54942c2ee056fa4f26a2a19cff7e0a265c1`, 38 модулей / 23 571 строка Basic,
29 листов ODS). Этот документ фиксирует конкретные проектные решения перед написанием кода.

## 0. Что заменяем и почему (привязка к найденным дефектам)

| Дефект 1.4.1 (подтверждён построчно) | Решение в PRIME |
|---|---|
| Расщеплённый commit: `WMS_10_DB_Stock.bas:373` коммитит движение, `WMS_12_DB_SmartReceipt.bas:355` коммитит партию отдельно — сбой между ними даёт движение без партии | Один `PRIME_PostDocument`: весь план документа (шапка, строки, партии, движения) собирается в памяти и пишется **одним** пакетным проходом, COMMITTED выставляется последним логическим шагом |
| Два несовместимых механизма возврата (модуль 08 `RET-`+двойной commit vs модуль 23 `SOURCE_ID`+один commit), старая кнопка возврата ещё жива | Один `RETURN`-тип документа в едином posting engine, привязка только через `SOURCE_KEY`/ссылку на исходную строку выдачи; старый путь не переносится |
| `WMSWF_IssueRowCon` (`WMS_20:461`) читает «Назначение», но не пишет его ни в один INSERT | Поле "Назначение / проект" — обязательное поле модели документа во всех формах выдачи, часть `DB_PRIME_DOC_LINES` |
| Два лока конкурентности не пересекаются (Orders: `gWMSORD_Busy`; Issues/Workshop: `WMSDBX_TryEnter`) — Orders и цеховой пост не исключают друг друга | Единый рантайм-лок `PRIME_TryEnter/PRIME_Leave` на уровне всего документа для любого проведения, независимо от листа-источника |
| `Orders_RebuildGroupContexts` при смене "групповой" колонки перечитывает и переписывает весь диапазон A1:Z (02:1278, 1824) | `PRIME_OnContentChanged` обрабатывает только изменившуюся строку через memory-index; полный пересчёт запрещён (`events.forbidden_actions`) |
| `WMSDBST_EnsureSchema`/`WMSARCH_EnsureSchema` выполняются на каждую позицию проведения | Миграция/EnsureSchema — разовая операция при открытии/обновлении, не часть posting-пути |
| `EnsureProductCon` (факт. `WMSDBST_EnsureProductCon`) вызывается до проверки повтора движения — может переписать карточку товара даже на дубликате | Порядок обязателен: сначала проверка `SOURCE_KEY` на COMMITTED-повтор, затем (и только тогда) любые изменения справочника товаров |
| `WMSDB_Close`: commit → store → close → store → close — неявно подтверждает недоопределённую операцию | Нет отдельного «закрытия БД»: `ThisComponent.store()` вызывается один раз в конце успешного проведения, транзакционное состояние (PREPARED/COMMITTED) хранится в `SYS_PRIME_TX` и переживает store независимо |
| 3 движка UI-раскладки (модули 19/31/37) с разными списками листов | Один `PRIME_12_UI`, одна команда "Восстановить интерфейс PRIME" |
| 2 реализации поиска (09 старая неиспользуемая, 24 живая) | Один `PRIME_09_StockSearch`, поиск по индексу, без параллельных путей |
| Перемещения и комплекты в 1.4.1 отсутствуют полностью | Проектируются с нуля как новые типы документов на общем posting engine, не миграция данных |
| Никакого события Open/Save/Close на уровне документа не было (office:scripts пуст) — `WMS_Close` вызывался только руками из кода | PRIME не полагается на закрытие приложения: любое непрошедшее до конца проведение обнаруживается при следующем открытии через `SYS_PRIME_TX` (crash recovery), а не через хук закрытия |

## 1. Системные листы (скрытые, `SYS_PRIME_*` / `DB_PRIME_*`)

Все системные листы: `system_sheets_rules.hidden=true`, без ручного редактирования, только пакетный I/O
через `PRIME_02_Store`. Остаток — это VIEW поверх `DB_PRIME_MOVEMENTS` (COMMITTED), не хранимое поле.

### SYS_PRIME_META
| Поле | Тип | Назначение |
|---|---|---|
| KEY | Text | версия схемы, версия сборки, дата установки |
| VALUE | Text | значение |

### SYS_PRIME_SEQ
| Поле | Тип |
|---|---|
| SEQ_NAME | Text (PRODUCT_CODE, ORDER_ID, DOC_ID, LOT_ID, MOVE_ID, KIT_ID, ACT_ID, INVENTORY_SESSION_ID, TRANSFER_ID) |
| NEXT_VALUE | Long |

`SequenceNext(seqName)` — единственная точка выдачи новых ID/кодов (см. `data_access_layer.helpers`).

### SYS_PRIME_TX (транзакционный журнал — сердце устойчивости)
| Поле | Тип |
|---|---|
| OP_ID | Text (уникальный, ULID-подобный: timestamp+random) |
| SOURCE_KEY | Text (идемпотентность, см. §4) |
| DOC_ID | Text |
| STATE | Text: PREPARED / COMMITTED / FAILED / CANCELLED |
| STARTED_AT / COMMITTED_AT | DateTime |
| HASH | Text (контрольная сумма плана документа) |
| ERROR | Text |

Остаток считается **только** по строкам с DOC_ID, чей OP_ID в COMMITTED. PREPARED-строки без COMMITTED
после перезапуска показываются в диагностике, не в остатке, и не доводятся автоматически (`crash_recovery`).

### DB_PRIME_PRODUCTS
`PRODUCT_CODE (PK, "ЕИ-00000001…"), PRODUCT_NAME, BASE_UNIT, DEFAULT_LOCATION, CATEGORY, SUBCATEGORY, RETURNABLE, ACCOUNT_TYPE, ACTIVE, CREATED_AT, UPDATED_AT`

### DB_PRIME_ALIASES
`ALIAS_ID, PRODUCT_CODE, PLATFORM ("От кого/площадка"), SELLER ("Продавец"), SUPPLIER_CODE, SUPPLIER_ARTICLE, COMMENT, ACTIVE`
Составной контекст соответствует legacy-листу «Сопоставления»; при неоднозначности — не угадывать, требовать выбор.

### DB_PRIME_PRODUCT_UNITS
`PRODUCT_CODE, UNIT_NAME, FACTOR_TO_BASE, ACTIVE` — конверсия своя для каждого товара, отсутствие фактора блокирует всё проведение.

### DB_PRIME_DOCUMENTS / DB_PRIME_DOC_LINES
Документ = header + lines, один формат для RECEIPT/ISSUE/RETURN/TRANSFER/ADJUSTMENT/ASSEMBLY/DISASSEMBLY.
`DOC_ID, DOC_TYPE, DOC_DATE, SOURCE_SHEET, SOURCE_KEY, ORDER_ID, STATUS` в шапке;
`DOC_LINE_ID, DOC_ID, PRODUCT_CODE, QTY_BASE, UNIT, PRICE, LOCATION_FROM, LOCATION_TO, DESTINATION_PROJECT, RECIPIENT, COMMENT` в строках.
Поле `DESTINATION_PROJECT` явно присутствует — закрывает потерю "Назначения" из 1.4.1.

### DB_PRIME_MOVEMENTS
`MOVE_ID, DOC_ID, DOC_LINE_ID, PRODUCT_CODE, LOT_ID, QTY_BASE (+/-), LOCATION, MOVE_DATE, OP_ID`
Единственный источник истины по складу (`stock_view.data_source`).

### DB_PRIME_LOTS
`LOT_ID, PRODUCT_CODE, RECEIPT_DOC_ID, RECEIPT_LINE_ID, RECEIPT_DATE, LOCATION, ORIGINAL_QTY_BASE, BASE_UNIT, ORIGIN, ORDER_ID`
Текущий остаток партии — сумма связанных COMMITTED движений, не хранимое поле.

### DB_PRIME_ALLOCATIONS
`ALLOC_ID, DOC_LINE_ID (issue), LOT_ID, QTY_BASE` — результат FIFO-разбиения одной строки выдачи на несколько партий.

### DB_PRIME_RETURNS
`RETURN_ID, ORIGINAL_ISSUE_DOC_LINE_ID, RETURN_DOC_ID, QTY_BASE, RETURN_DATE`
Одна реализация вместо конфликтующих 08/23; лимит = `issued_qty - already_returned_qty`.

### DB_PRIME_ORDER_SNAPSHOT
Неизменяемый снимок заказа на момент каждой поставки: все 25 бизнес-полей листа «Заказы» + `RECEIPT_DOC_ID, LOT_ID, DELIVERY_QTY` (используется листом «Остаток — Заказы», не пересчитывается задним числом).

### DB_PRIME_KITS / DB_PRIME_KIT_LINES
`KIT_ID, Название, Версия, Активен` / `KIT_ID, PRODUCT_CODE, QTY_PER_KIT, UNIT`. Режим первой версии — только "набор для выдачи" (виртуального остатка комплекта не создаём); физическая сборка/разборка — архитектурно готовы, не обязательны для первого релиза.

### DB_PRIME_ACTS
`ACT_ID, DOC_ID, FILE_PATH, GENERATED_AT, STATUS` — акт всегда строится по DOC_ID из сохранённого документа, не из текущего выделения.

### DB_PRIME_AUDIT
`TS, OP_ID, STAGE, DURATION_MS, SHEET, ROW, ERROR_NO, ERROR_TEXT` — соответствует `logging.stages`.

## 2. Транзакционная модель / единый posting engine

`PRIME_PostDocument(docType, planInMemory)` — единственная функция, которая пишет в системные листы
(`data_access_layer.only_store_layer_directly_accesses_hidden_db_sheets`). Алгоритм (см. ТЗ `posting_algorithm`,
здесь — конкретизация под найденные дефекты):

1. `PRIME_TryEnter()` — единый рантайм-лок (закрывает дыру "Orders и Issues не исключают друг друга").
2. `PRIME_EventEnter()` — guard для событий (вложенный счётчик, не boolean — предотвращает баг класса `Orders_CreateNewEntryWithSource`, который снимал busy-флаг раньше времени).
3. Прочитать документ пользователя целиком в память (`getDataArray`), построить план: header, lines, products (создание ЕИ-кода при необходимости), lots, FIFO allocations (для ISSUE), movements, returns/links, order snapshot (для RECEIPT).
4. Проверить: остаток по каждой строке (ISSUE/TRANSFER), единицы и конвертации (блокировка всего документа при отсутствии фактора), повтор `SOURCE_KEY` среди COMMITTED — **до** любого изменения `DB_PRIME_PRODUCTS`.
5. Записать `SYS_PRIME_TX` со STATE=PREPARED.
6. Пакетно (`setDataArray`, батчами) записать DOCUMENTS/LINES/PRODUCTS/LOTS/ALLOCATIONS/MOVEMENTS/RETURNS/SNAPSHOT.
7. Обновить `SYS_PRIME_TX` → COMMITTED (последний логический шаг перед UI).
8. Обновить интерфейс, один раз `ThisComponent.store()`.
9. Только после успешного store — очистка разрешённых полей ввода.
10. `PRIME_Leave()`/`PRIME_EventLeave()` — всегда, включая аварийные ветки (единая cleanup-подпрограмма, не `On Error Resume Next` вокруг записи).

Нехватка на любой строке ISSUE отменяет **весь** документ (`fifo.shortage_behavior`), а не только строку.

## 3. Идемпотентность (SOURCE_KEY)

| Операция | SOURCE_KEY |
|---|---|
| Приход по заказу | ORDER_ID + ORDER_LINE_ID + DELIVERY_ID |
| Выдача | ISSUE_DRAFT_ID |
| Возврат | ORIGINAL_ISSUE_LINE_ID + RETURN_ID |
| Инвентаризация | INVENTORY_SESSION_ID + LINE_ID |
| Перемещение | TRANSFER_DOC_ID |

Повторный клик с уже COMMITTED SOURCE_KEY: новых движений не создавать, вернуть существующий DOC_ID,
статус "Уже проведено" — закрывает найденный в 1.4.1 риск двойного возврата через старую кнопку.

## 4. События листов

Единственный разрешённый обработчик — `PRIME_OnContentChanged`, по одному на лист ввода
(Заказы, Выдачи, 4 актуальных цеховых/офисных листа). Логика идентична для всех — не повторяем
проблему 1.4.1, где Orders и Issues имели разные, несовместимые guard-механизмы:
- определить изменившуюся строку и колонку;
- игнорировать технические колонки;
- при вводе внутреннего кода — точечный lookup по memory-index (никогда не полный пересчёт диапазона, что было причиной зависаний в `Orders_RebuildGroupContexts`);
- если положительный остаток товара ровно в одном месте — подставить «Откуда», иначе оставить пустым.

Групповые реквизиты (аналог `Orders_GroupRelevantChange`) в PRIME не пересчитываются построчным сканированием
всего листа при каждом вводе — группировка вычисляется на чтении (при построении отчётов/остатков), а не
поддерживается императивно в фоне.

## 5. Что переносим 1:1, что меняем, что строим заново

| Лист/фича 1.4.1 | Статус в PRIME |
|---|---|
| Заказы (25 бизнес-колонок + партиальные поставки) | Переносится: те же колонки, + `Получено всего`/`Осталось получить` уже есть в ТЗ; тех-колонки заменяются на 3 скрытых helper (`_PRIME_OrderID/LineID/State`) вместо 10 `_WMS_*` |
| Выдачи (12 бизнес-колонок + возврат) | Переносится, + обязательное `Назначение / проект` |
| Приход/Расход — Цех, Офис (4 активных листа) | Переносятся как единый workflow-механизм на общем posting engine |
| Приход/Расход — Производство, Детали (4 архивных листа) | Не переносятся как формы ввода: скрываются/только чтение, данные мигрируют как история (`legacy_parallel_forms`) |
| Возврат (модуль 08, кнопка на «Выдачи») | Не переносится: заменяется единым RETURN-документом; кнопка отключается |
| Возвраты (модуль 23, лист «Возвраты») | Переносится как единственный механизм возврата |
| Инвентаризация | Переносится, добавляется проверка движений после снимка (конфликт → явная обработка) |
| Остаток / Остаток — Заказы | Переносятся как view поверх COMMITTED-движений и снимков заказа соответственно |
| База - Поиск (модуль 24, живой) | Переносится как единственная реализация поиска; модуль 09 (мёртвый код) не переносится |
| Акты (ODT) | Переносятся, строятся по DOC_ID, не по текущему выделению |
| Комплекты | Новая функциональность (в 1.4.1 отсутствует) |
| Перемещения | Новая функциональность (в 1.4.1 отсутствует) |
| Дашборд, Отчёт руководителю | Переносятся с явным снимком времени обновления |
| Диагностика WMS | Переносится как реально read-only (без скрытого commit/store через общий Close) |
| WMS_DATA_PORTABLE.odb (Firebird) | Не требуется в рантайме; опционально — одноразовый read-only импорт истории |

Соответствие функциональности §5 пятнадцати модулям `PRIME_00`…`PRIME_14` — без изменений от ТЗ,

## 7. Тестовый план (детализация `model_tests`/`acceptance_tests` под найденные дефекты)

Дополнительно к кейсам из ТЗ, обязательные регрессионные тесты на конкретные дефекты 1.4.1:
- одновременное проведение из Заказов и из цехового листа не создаёт гонки (единый `PRIME_TryEnter`);
- повторное нажатие старой-аналогом кнопки возврата после уже проведённого возврата не создаёт второе движение;
- поле «Назначение» сохраняется в `DB_PRIME_DOC_LINES` после проведения и после очистки формы;
- сбой между записью партии и движения (fault injection `AFTER_LOTS`) не оставляет движение без партии.
